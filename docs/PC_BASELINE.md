# PC Baseline (M0)

The PC Steam release of Quake 4, used as (a) the data reference to diff the 360 disc against later, and (b) the target for a native openQ4 build that serves as our performance and visual baseline.

## PC install

`E:\SteamLibrary\steamapps\common\Quake 4`: Steam build of the 1.4.x patch level (`CHANGES_14.txt`), 2.9 GB.

| Item | Notes |
|---|---|
| `Quake4.exe`, `Quake4Ded.exe` | 32-bit engine (client / dedicated) |
| `q4base/gamex86.dll` | SP game DLL, built from the code the Q4 SDK ships |
| `q4base/pak001`–`pak025.pk4`, `zpak_english*.pk4`, `q4cmp_pak001.pk4` | Assets, plus English localisation and community map pack |
| `q4base/game000`–`game300.pk4`, `q4mp/game*.pk4` | Game DLLs for Linux/macOS (`game.so.bundle`), one per patch level |

## Data inventory

Generated by `python -I tools/pk4_index.py "<install>" inventory/pc`. The output is gitignored and holds paths, sizes and CRCs only.

- **40 pk4s, 32,702 files**. 484 paths appear in more than one pak (later paks override earlier ones).
- Largest content types: `.tga` 11,099 files / 4.1 GB uncompressed, `.dds` 8,454 / 0.85 GB, `.ogg` 5,737, `.md5anim` 2,233, `.cm` (collision) 983 / 1.0 GB, `.proc` 102 / 0.9 GB.
- Renderer programs live in `glprogs/` (58 ARB `.vp`/`.fp`/`.vfp`), which is the PC equivalent of the shaders XenosRecomp will handle on 360.
- **No console leftovers in PC data:** nothing named xbox, xenon or 360, and no joystick/gamepad configs or GUIs. PC Quake 4 shipped with no controller support at all, so every bit of 360 controller UI and tuning has to come from the 360 disc.

What to diff once the 360 disc is dumped:
- `guis/` for the controller-first menus
- `def/` and `cfg/` for aim assist and stick-curve tuning
- `textures/` resolution for 360 texture quality vs PC (DDS mip counts)
- `maps/*.proc`: did Raven split or simplify levels for 360 memory?

## Key finding: the 360 game code is already in the SDK source

Raven's Quake 4 SDK, which openQ4 carries in `src/game` and `src/mpgame`, was never stripped of its Xbox 360 code. **70 files contain 232 `_XENON`/`_XBOX` blocks.** They're compiled out on PC, but the source is right there:

- **360 aim assist** (`src/game/Player.cpp` ~7555–7701, cvars in `src/game/gamesys/SysCvar.cpp:443`). The comment says "parameters for aim assistance on Xenon". It has two modes (`pm_AimAssist 1` bends the view, `2` bends the muzzle aim), plus:
  - targeting: a frustum of `pm_AimAssistFOV` (10%) out to `pm_AimAssistDistance` (1000 units)
  - muzzle correction: `pm_AimAssistBump` (10%)
  - **friction**: turn speed slowed to `pm_AimAssistSlow` (50%) while on target, through `usercmdGen->SetSlowJoystick()`
  - a slower zoomed turn speed: `pm_zoomedSlow`
  - per-weapon `AllowAutoAim()` / `GetAutoAimFOV()`
- Also `_XENON` paths in idlib/math, decls, the renderer headers and multiplayer.

**What's missing:** the **engine** half. `idUsercmdGen::SetSlowJoystick` and the 360 stick-processing code (dead zones, response curve, acceleration) are not in openQ4 or the SDK. The SDK only ever shipped game code. openQ4 has its own SDL3 controller code with different tuning (`in_joystickLookCurve` 1.35, dead zone 0.18), no friction hook, and no aim assist enabled.

→ **The top M1 recon target in the 360 `default.xex`** is to recover `idUsercmdGen`'s joystick path and `SetSlowJoystick`, plus the shipped 360 default values for the `pm_AimAssist*` cvars. Those values may differ from the SDK defaults; check the 360 `default.cfg`/`.def` data.

## openQ4 native build

Built 2026-10-21 from `reference/openQ4` @ `cbe967f` (0.11.0-dev), Windows x64 release, **VS 2022 / MSVC 19.44**. openQ4 recommends 19.46 (VS 2026), but it isn't enforced and the build is clean. All 1937 steps passed: client, dedicated server, `renderer-gl` + `renderer-vk`, `game-sp` + `game-mp`.

### Recipe (PowerShell)

```powershell
# one-time
python -m pip install --user meson ninja      # must be python.exe, not the free-threaded python3.13t
cd reference\openQ4
pwsh -File tools/build/prepare_windows_openal.ps1 -Architecture x64   # needs PowerShell 7; falls back to NuGet openal.soft 1.23.1

# each build: drop PATH entries that break cmd.exe (the DSX entry under "Program Files (x86)" does)
$env:PATH = "$env:APPDATA\Python\Python313\Scripts;" + (($env:PATH -split ';' | ? { $_ -and $_ -notmatch 'DSX' }) -join ';')
$env:OPENQ4_OPENAL_ROOT = "$PWD\.tmp\openal-soft-windows-x64"
powershell -ExecutionPolicy Bypass -File tools/build/meson_setup.ps1 setup builddir . --backend ninja --buildtype=release --wrap-mode=forcefallback
powershell -ExecutionPolicy Bypass -File tools/build/meson_setup.ps1 compile -C builddir
```

Gotchas we hit:
1. `meson_setup.ps1` imports `mesonbuild` through `python.exe`. Meson installed only into `python3.13t` fails.
2. A PATH entry `C:\Program Files (x86)\Steam\steamapps\common\DSX\...` makes `VsDevCmd.bat` fail with "...was unexpected at this time". The fix is to filter it out for the build shell only.
3. `OpenAL32.dll` is gitignored upstream. The final staging step fails until `OPENQ4_OPENAL_ROOT` points at a prepared package.

### Run

```powershell
reference\openQ4\builddir\openQ4-client_x64.exe +set fs_savepath "<repo>\reference\openQ4\.home"
```

Steam data is auto-discovered through `libraryfolders.vdf` (`OPENQ4_QUAKE4_PATH` overrides it). The log is `.home\baseoq4\qconsole.log`.

### First run (smoke test)
- Found `E:\SteamLibrary\...\Quake 4\q4base` automatically and loaded all 31 retail paks plus openQ4's `pak0`/`pak1`.
- Hardware: Ryzen 7 9800X3D, 24 GB NVIDIA GPU, AW3225QF **3840×2160 @ 240 Hz**. Auto-selected the `balanced` preset.
- Renderer: OpenGL 4.6 compat, 8× MSAA, vsync off (swap interval 0). Vulkan is available through `r_renderApi vulkan`.
- **Controller: `XInput Controller #1` opened through SDL3 gamepad** with no setup.
- Reached the main menu with 0 errors. One harmless warning: `main_menu` sound decl not pre-cached.

### Controller fix: multiple Xbox pads (patch 0002)
On this PC SDL sees **four** Xbox-type gamepads: `XInput#0` "XInput Controller #1", two virtual "Xbox 360 Controller"s (Nefarius ViGEm / Oculus / Steam virtual pad drivers are installed), and the real Bluetooth **Xbox Series X Controller** on `XInput#3`. Upstream openQ4 opens only the first gamepad, and SDL3 only delivers events for opened gamepads, so the real pad gave **no input at all** (`listControllers` shows the list).

[`patches/openq4/0002-sdl3-follow-active-gamepad.patch`](../patches/openq4/0002-sdl3-follow-active-gamepad.patch) keeps every other gamepad open on standby. The first button press, or a stick or trigger past half travel, on a standby pad makes it the active one. The log shows `controller: N more gamepad(s) on standby` at startup and `switched to the gamepad in use` on handover. Confirmed working with the user's Xbox Series X controller on 2026-10-21. This is worth sending upstream to openQ4.

Note: openQ4 sets `SDL_HINT_JOYSTICK_ALLOW_BACKGROUND_EVENTS=0`, so the game window must have focus for any controller input.
